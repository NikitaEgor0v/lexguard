# Краевые Случаи и Риски Архитектуры (Edge Cases & Risks)

В ходе аудита кодовой базы были выявлены потенциально "хрупкие" места, которые могут стать причиной ошибок или ухудшения пользовательского опыта. Ниже перечислены основные краевые случаи и технические компромиссы текущей архитектуры LexGuard.

## 1. Лимиты на размер документа
**Где:** `api/routes.py`, `services/analyzer.py`
**Суть:** Документы обрабатываются последовательно — каждый сегмент анализируется отдельно. Прогресс сохраняется в Redis.
**Риск:** Очень крупные документы требуют значительного времени обработки. При недостатке GPU/RAM может произойти OOM на уровне Ollama.

## 2. Определение типа контракта по началу текста
**Где:** `services/analyzer.py` -> `_classify_contract_type()`
**Суть:** Для определения типа договора LLM анализирует только первые один или два сегмента (до 800 символов). 
**Риск:** В российских реалиях преамбула (указание сторон, оснований действий) может быть очень длинной. Если слово "Договор подряда" находится за пределами первых 800 символов, система неверно классифицирует договор как `"иной"`, что приведет к снижению релевантности RAG-поиска (будут искаться только универсальные нормы).

## 3. Зависание UI при "падении" Celery-таски
**Где:** Взаимодействие `routes.py`, `analyzer.py` и Redis.
**Суть:** Фронтенд опрашивает статус `/analyze/{id}`. Бэкенд читает статус из Redis (`progress:{id}`). Если Celery worker внезапно падает (например, OOM или краш контейнера) в середине процесса, ключ в Redis просто протухнет (установлен TTL 3600 секунд). 
**Риск:** Фронтенд может "зависнуть" в бесконечном поллинге или показывать устаревший статус, так как нет явного механизма передачи статуса `failed` из Celery в БД, если worker был убит системой (SIGKILL).

## 4. Скрытый (Silent) Fallback парсера JSON
**Где:** `services/analyzer.py` -> `_parse()`
**Суть:** Если LLM галлюцинирует и возвращает невалидный JSON, метод `_parse()` перехватывает исключение и возвращает захардкоженный ответ: `is_risky=True`, `risk_level=LOW`, `recommendation="Проверьте вручную"`.
**Риск:** Настоящие ошибки генерации (или пустые ответы) скрываются от разработчика. Вместо того, чтобы логировать критическую проблему или пере-генерировать ответ, система маскирует ошибку под "слабый риск". При массовой галлюцинации документ будет усеян "низкими" рисками без реального анализа.

## 5. Тихие ошибки Redis
**Где:** `services/analyzer.py` → `analyze()`
**Суть:** При обновлении прогресса анализ ловит `Exception` при работе с Redis и игнорирует его (`pass`). 
**Риск:** Это повышает аптайм (анализ не падает, если упал Redis), но при этом ломается UX на клиенте — прогресс-бар просто замирает на 0% до самого конца анализа.

## 6. Последовательная обработка
**Где:** `services/analyzer.py` → `analyze()`
**Суть:** Сегменты анализируются последовательно в цикле `for`. Каждый сегмент обрабатывается полностью перед переходом к следующему.
**Преимущество:** GPU получает все ресурсы на один запрос, что важно для маленьких моделей (gemma2:2b). Стабильнее работает на слабом железе.
**Риск:** Медленнее, чем параллельная обработка. Для крупных документов время ожидания может быть значительным.

## 7. Галлюцинации LLM
**Где:** `services/analyzer.py` → `SYSTEM_PROMPT`, `_parse()`
**Суть:** LLM может галлюцинировать, особенно при использовании RAG-контекста. Модель может "импортировать" риски из норм, которых нет в тексте сегмента.
**Риск:** False positives или false negatives. Модель может пометить безопасный сегмент как рисковый (или наоборот).
**Защита:**
- Промпт содержит явные указания анализировать только текст сегмента
- Правило: "не приписывай фрагменту риски, которых в его тексте нет"
- При ошибке парсинга JSON возвращается LOW риск с рекомендацией проверить вручную

## Решённые проблемы (Май 2026)

### P0: Безопасность API
- ✅ **IDOR Protection**: Добавлена проверка владельца для всех эндпоинтов анализа и чата
- ✅ **404 для несуществующих анализов**: Вместо ложного `processing` возвращается корректный 404
- ✅ **Heartbeat-based failure detection**: Анализы с устаревшим heartbeat автоматически помечаются как `failed`

### P1: Логика анализа и RAG
- ✅ **Инкрементальное сохранение**: Результаты сохраняются пакетами по `ANALYSIS_BATCH_SIZE` (20) сегментов
- ✅ **User documents в RAG**: Пользовательские эталоны интегрированы в основной RAG pipeline
- ✅ **Детерминированное слияние контекстов**: System chunks → User chunks с приоритетом

### P2: Целостность данных
- ✅ **CHECK constraints**: status, risk_level, role ограничены допустимыми значениями
- ✅ **UNIQUE constraint**: (analysis_id, segment_id) предотвращает дубликаты сегментов

## Оставшиеся рекомендации
1. Увеличить контекст для классификации типа документа или искать ключевые слова (regex) по всему документу перед вызовом LLM.
2. Добавить счетчик "сломанных JSON" на один документ. Если LLM ошибается в >20% сегментов, прерывать анализ и выдавать ошибку генерации.
3. Для крупных документов рассмотреть опциональное включение параллельной обработки на мощном железе (требует настройки `LLM_MAX_WORKERS`).

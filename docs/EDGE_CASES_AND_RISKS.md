# Краевые случаи и риски архитектуры

Потенциально хрупкие места, которые могут стать причиной ошибок или ухудшения UX.

---

## Активные проблемы

### 1. Определение типа контракта по началу текста

**Где:** `services/analyzer.py` → `_classify_contract_type()`

**Суть:** Для определения типа LLM анализирует до 1500 символов (`MAX_CLASSIFY_PREVIEW_CHARS`). `PreprocessorService.extract_smart_classification_preview()` дополнительно читает середину документа и ищет маркеры сторон через regex.

**Риск:** В российских реалиях преамбула может быть длинной. Если ключевые слова не попали в превью — система классифицирует как `"иной"`, что снижает релевантность RAG-поиска.

**Митигация:** regex-маркеры помогают даже без LLM определить тип по наименованию сторон.

### 2. Зависание UI при падении Celery

**Где:** Взаимодействие `routes.py`, `analyzer.py` и Redis.

**Суть:** Если Celery worker падает (OOM, SIGKILL), ключ в Redis протухает по TTL. Heartbeat-detection помечает анализ как `failed` при устаревшем heartbeat.

**Риск:** Между падением и детекцией (до `LLM_HEARTBEAT_TIMEOUT = 600` сек) фронтенд показывает устаревший статус.

### 3. Silent Fallback парсера JSON

**Где:** `services/analyzer.py` → `_parse()`

**Суть:** При невалидном JSON от LLM возвращается `is_risky=True, risk_level=LOW, recommendation="Проверьте вручную"`.

**Риск:** Ошибки генерации маскируются под слабые риски. При массовой галлюцинации документ будет усеян "низкими" рисками без реального анализа.

### 4. Тихие ошибки Redis

**Где:** `services/analyzer.py` → `analyze()`

**Суть:** При обновлении прогресса `Exception` ловится и игнорируется.

**Риск:** Аптайм не падает, но прогресс-бар замирает на 0% до самого конца.

### 5. Расхождение MIN_RELEVANCE_SCORE

**Где:** `config/model_registry.py`, `.env.example`, `docker-compose.yml`

**Суть:** `MIN_RELEVANCE_SCORE_DEFAULT = 0.80` в коде, но `docker-compose.yml` и `.env.example` передают `0.50`. Итоговое поведение зависит от того, есть ли env-переменная в runtime.

**Риск:** На свежем деплое с docker-compose будет использоваться `0.50` (из env), что может давать больше нерелевантного RAG-контекста.

### 6. Последовательная обработка

**Где:** `services/analyzer.py` → `analyze()`

**Суть:** Все сегменты обрабатываются последовательно в цикле.

**Преимущество:** GPU получает все ресурсы, стабильно на слабом железе.

**Риск:** Крупные документы (200+ сегментов) могут обрабатываться 30-60 минут.

## Решённые проблемы

### Безопасность (P0)
- IDOR Protection для всех эндпоинтов анализа и чата
- 404 для несуществующих анализов (вместо ложного `processing`)
- Heartbeat-based failure detection (stale → `failed`)

### Логика анализа (P1)
- Инкрементальное сохранение пакетами по 20 сегментов
- User documents в RAG с детерминированным слиянием
- RAG-контаминация: повышен порог, исправлен эмбеддинг (safe_norm + risky_pattern)
- safe_redaction: SequenceMatcher вместо множеств, DANGEROUS_PHRASES

### Целостность данных (P2)
- CHECK constraints для status, risk_level, role
- UNIQUE constraint для (analysis_id, segment_id)

### Frontend/UX
- Кнопка "Анализировать" при загрузке нового файла
- Nginx proxy recovery после рестарта backend (Docker DNS resolver)
- Typing indicator с Page Visibility API
- Чат: pendingSessions, нумерация рисков

### LLM / Промпт
- Критическое правило сравнения ЭТАЛОН vs РИСК
- 11 категорий нейтральных сегментов в промпте
- Откат от ANTI-CONTAMINATION (слишком жёстко для 2B)
- Расширенные возможности AI-ассистента в чате

---

## Рекомендации на будущее

1. **Счётчик ошибок JSON**: Если LLM ошибается в >20% сегментов — прерывать анализ и выдавать ошибку.
2. **Параллельная обработка**: Опционально для мощного железа (через `LLM_MAX_WORKERS`).
3. **Синхронизация порогов**: Привести `MIN_RELEVANCE_SCORE` к единому значению между env и кодом.
4. **Websocket вместо polling**: Для более быстрого отображения прогресса.

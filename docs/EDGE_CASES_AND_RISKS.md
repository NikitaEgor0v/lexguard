# Краевые Случаи и Риски Архитектуры (Edge Cases & Risks)

В ходе аудита кодовой базы были выявлены потенциально "хрупкие" места, которые могут стать причиной ошибок или ухудшения пользовательского опыта. Ниже перечислены основные краевые случаи и технические компромиссы текущей архитектуры LexGuard.

## 1. Лимиты на размер документа
**Где:** `api/routes.py`, `services/analyzer.py`
**Суть:** Максимальное число сегментов настраивается через переменную `MAX_SEGMENTS_PER_DOCUMENT` (по умолчанию 500, 0 = без лимита). Документы обрабатываются пакетами по `ANALYSIS_BATCH_SIZE` (по умолчанию 20 сегментов). Каждый пакет сохраняется в БД инкрементально — фронтенд может отображать результаты по мере готовности.
**Риск:** Очень крупные документы (500+ сегментов) требуют значительного времени обработки. При недостатке GPU/RAM может произойти OOM на уровне Ollama.

## 2. Определение типа контракта по началу текста
**Где:** `services/analyzer.py` -> `_classify_contract_type()`
**Суть:** Для определения типа договора LLM анализирует только первые один или два сегмента (до 800 символов). 
**Риск:** В российских реалиях преамбула (указание сторон, оснований действий) может быть очень длинной. Если слово "Договор подряда" находится за пределами первых 800 символов, система неверно классифицирует договор как `"иной"`, что приведет к снижению релевантности RAG-поиска (будут искаться только универсальные нормы).

## 3. Зависание UI при "падении" Celery-таски
**Где:** Взаимодействие `routes.py`, `analyzer.py` и Redis.
**Суть:** Фронтенд опрашивает статус `/analyze/{id}`. Бэкенд читает статус из Redis (`progress:{id}`). Если Celery worker внезапно падает (например, OOM или краш контейнера) в середине процесса, ключ в Redis просто протухнет (установлен TTL 3600 секунд). 
**Риск:** Фронтенд может "зависнуть" в бесконечном поллинге или показывать устаревший статус, так как нет явного механизма передачи статуса `failed` из Celery в БД, если worker был убит системой (SIGKILL).

## 4. Скрытый (Silent) Fallback парсера JSON
**Где:** `services/analyzer.py` -> `_parse()`
**Суть:** Если LLM галлюцинирует и возвращает невалидный JSON, метод `_parse()` перехватывает исключение и возвращает захардкоженный ответ: `is_risky=True`, `risk_level=LOW`, `recommendation="Проверьте вручную"`.
**Риск:** Настоящие ошибки генерации (или пустые ответы) скрываются от разработчика. Вместо того, чтобы логировать критическую проблему или пере-генерировать ответ, система маскирует ошибку под "слабый риск". При массовой галлюцинации документ будет усеян "низкими" рисками без реального анализа.

## 5. Тихие ошибки Redis
**Где:** `services/analyzer.py` → `analyze()`
**Суть:** При обновлении прогресса анализ ловит `Exception` при работе с Redis и игнорирует его (`pass`). 
**Риск:** Это повышает аптайм (анализ не падает, если упал Redis), но при этом ломается UX на клиенте — прогресс-бар просто замирает на 0% до самого конца анализа.

## 6. Параллельная обработка и перегрузка Ollama
**Где:** `services/analyzer.py` → `analyze()`, `_analyze_single_segment()`
**Суть:** Сегменты анализируются параллельно через `ThreadPoolExecutor` с числом потоков `LLM_MAX_WORKERS` (по умолчанию 3). Одновременно в Ollama уходит до `LLM_MAX_WORKERS` запросов.
**Риск:** Если `LLM_MAX_WORKERS` превышает `OLLAMA_NUM_PARALLEL` или возможности GPU/RAM сервера, Ollama может упасть с OOM (Out of Memory). Рекомендуемые значения:
- **8 GB VRAM**: `LLM_MAX_WORKERS=2`
- **16 GB VRAM**: `LLM_MAX_WORKERS=3`
- **24+ GB VRAM**: `LLM_MAX_WORKERS=4-5`
**Защита:** При ошибке отдельного сегмента поток не роняет весь анализ — для него создается fallback-запись с `risk_level=LOW`.

## 7. Галлюцинации в safe_redaction (Безопасная формулировка)
**Где:** `services/analyzer.py` → `SYSTEM_PROMPT`, `_parse()`, `_validate_safe_redaction()`
**Суть:** LLM предлагает переписанный текст пункта для устранения рисков (поле `safe_redaction`). Модель ограничена промптом: она обязана опираться только на RAG-контекст и общие нормы ГК РФ.
**Риск:** LLM может галлюцинировать, скопировать оригинал дословно или добавить пояснения в скобках вместо реальной переработки. Safe_redaction — это **черновое предложение**, а не юридически выверенный текст.
**Защита:**
- Промпт требует ЗАМЕНУ опасных формулировок, а не пояснения.
- Метод `_validate_safe_redaction()` отбрасывает safe_redaction, если он идентичен оригиналу или совпадает с ним на >90%.
- Для `low` и `none` рисков поле принудительно возвращается как `null`.
- На UI стоит отметка «Исправленный текст» — юрист всегда должен проверять предложение перед вставкой.

## 8. Контаминация RAG-контекстом (False Positives)
**Где:** `services/analyzer.py` → `SYSTEM_PROMPT_COMPACT`, `SYSTEM_PROMPT_FULL`, `_call_llm()`
**Суть:** При анализе нейтрального сегмента модель может "импортировать" риски из RAG-контекста — то есть пометить сегмент как рисковый только потому, что рядом оказалась норма с описанием опасной ситуации.
**Риск:** False positive на нейтральных сегментах (например, "Стоимость услуг составляет 100 000 рублей" помечается как рисковый). Также возможно смешение нескольких RAG-тем в одном `risk_description`.
**Защита:**
- В системных промптах добавлены блоки **АНТИ-КОНТАМИНАЦИЯ** и **ОДНА ТЕМА — ОДИН РИСК** с явными запретами.
- User prompt структурно разделяет фрагмент и нормы визуальными разделителями (`═══`), с пометками "анализируй ТОЛЬКО этот текст" / "НЕ переноси эти риски".
- Инструкция в конце user prompt дополнительно акцентирует: "Риск должен следовать из текста фрагмента, а не из норм".

## Рекомендации по устранению
1. Внедрить механизм обработки "мертвых" Celery-задач с таймаутом, чтобы переводить анализ в статус `error`.
2. Увеличить контекст для классификации типа документа или искать ключевые слова (regex) по всему документу перед вызовом LLM.
3. Добавить счетчик "сломанных JSON" на один документ. Если LLM ошибается в >20% сегментов, прерывать анализ и выдавать ошибку генерации.
4. При настройке параллельной обработки убедиться, что `LLM_MAX_WORKERS` ≤ `OLLAMA_NUM_PARALLEL` и соответствует ресурсам сервера.
5. Для safe_redaction — рассмотреть введение второго LLM-прохода для валидации предложенной формулировки (cost vs quality trade-off).

# RAG и Бизнес-логика

Модуль Legal Analyzer использует подход RAG (Retrieval-Augmented Generation) для предоставления LLM правового контекста перед принятием решения о наличии риска.

## 1. Векторизация и база данных (Qdrant)

За хранение и поиск эталонных правовых норм отвечает сервис `Qdrant`. 

- **Модель энкодера:** `intfloat/multilingual-e5-base`
- **Размерность вектора:** 768
- **Метрика дистанции:** Cosine Distance
- **Коллекция:** `legal_norms`

Все эталонные нормы (хранящиеся в `data/legal_norms.json`) преобразуются в векторы и помещаются в коллекцию Qdrant. Для каждой нормы сохраняются метаданные (payload): тип договора, категория риска, критичность, юридические паттерны и паттерны уловок.

## 2. Определение типа контракта

Перед началом покомпонентного RAG-анализа, система выполняет пред-анализ документа:
1. Берется превью договора: первый или два первых сегмента документа. Текст обрезается до 800 символов (`MAX_CLASSIFY_PREVIEW_CHARS`).
2. Превью отправляется в Ollama с промптом `CONTRACT_CLASSIFY_PROMPT`.
3. LLM определяет тип контракта (например, "аренда", "подряд", "нда").
4. Если LLM ошибается или не может определить, по умолчанию устанавливается тип `"иной"`.

## 3. RAG-поиск и фильтрация

Для каждого сегмента договора, который анализируется, происходит следующий алгоритм:

1. Сегмент переводится в вектор (`query: {текст}`).
2. Формируется объект фильтрации (`Filter` / `FieldCondition`), который требует совпадения поля `contract_type` с определенным типом контракта (с учетом алиасов) или универсальными типами (`все`, `all`).
3. Qdrant ищет ближайших соседей. Количество: `max_rag_norms` (2 для gemma2:2b). По умолчанию `TOP_K = 6` (с последующей фильтрацией).
4. Минимальный порог отсечения `MIN_RELEVANCE_SCORE = 0.72` (конфигурируется через env). Значение 0.72 выбрано как компромисс: оно достаточно жесткое для фильтрации нерелевантного RAG-контекста и устранения контаминации, но оставляет запас для тестирования по сравнению со строгим порогом 0.75. Все, что имеет сходство ниже — отбрасывается.
5. **Умная обрезка:** После сборки контекста происходит обрезка по `max_rag_chars` (800 для 2B), но всегда по границам норм (метод `_truncate_by_norm_boundaries`). Норма никогда не обрезается посередине — лишние нормы отбрасываются целиком.

### Интеграция пользовательских эталонов (P1)

Если пользователь загрузил свои кастомные документы (`user_id` передан), система производит **объединённый поиск**:

1. **Системные нормы** (коллекция `legal_norms`) — высший приоритет
2. **Пользовательские эталоны** (коллекция `user_documents`) — персональный контекст

Детерминированное слияние:
- Системные chunks идут первыми (юридический авторитет)
- Пользовательские chunks следуют (персональные стандарты)
- Общий лимит: `MAX_CHUNKS_PER_SEGMENT` (по умолчанию 3)
- Минимум 1 слот резервируется для пользовательского chunk, если есть документы

## 4. LLM Анализ (Ollama)

Найденные эталонные нормы (стандартные и пользовательские) конкатенируются и вставляются в промпт для LLM вместе с самим сегментом.

- **Системный промпт:** Один описательный промпт `SYSTEM_PROMPT` (~2500 символов) с точными критериями для классификации `risk_level` (high, medium, low, none) и `risk_category`.

### Логика сравнения с эталоном (критическое правило)

RAG-контекст содержит два ключевых поля для каждой нормы:
- **«Эталон:»** — безопасная, сбалансированная формулировка (образец)
- **«Риск:»** — опасный паттерн, который нужно выявлять

Критическое правило сравнения:
- Если текст фрагмента **СООТВЕТСТВУЕТ полю «Эталон»** (по смыслу или дословно) → `is_risky: false`, `risk_level: none`
- Если текст фрагмента **СООТВЕТСТВУЕТ полю «Риск»** → `is_risky: true`, определяется risk_level по тяжести
- Само по себе наличие RAG-контекста **НЕ означает наличие риска**. RAG показывает тему — решение принимается по ТЕКСТУ фрагмента.

### Нейтральные сегменты

Следующие типы сегментов автоматически классифицируются как `is_risky: false`:
- Только сумма договора ("180 000 рублей")
- Реквизиты (количество экземпляров, дата вступления в силу, адреса, ИНН)
- Подписи сторон, печати, должности
- Порядок внесения изменений через дополнительные соглашения (защита, не риск)
- Стандартные сроки уведомлений (3-10 рабочих дней)

### Правила классификации risk_level

- `high`: штрафы без лимита, утрата прав без компенсации, неограниченная ответственность
- `medium`: размытые сроки, неопределённые обязательства, одностороннее изменение условий
- `low`: незначительные огрехи формулировки
- `none`: нейтральный, сбалансированный текст или нейтральный сегмент

### Safe Redaction

Для рисков уровня `high` модель генерирует `safe_redaction` — безопасную переформулировку текста:
- Содержит ТОЛЬКО новую безопасную формулировку
- НЕ содержит исходный опасный текст
- Валидируется на overlap с оригиналом (<60%)

- **Генерация:** Запрос отправляется в Ollama с параметрами конфигурации модели (задается через `get_model_config()`).
- **Последовательная обработка:** Сегменты анализируются один за другим, GPU получает все ресурсы на каждый запрос.
- **Фоллбек (Fallback):** Если Ollama недоступна, используется ручной метод на основе ключевых слов (словарный метод в `rag._fallback()`), который возвращает предупреждения по базовым категориям.
- **Дедупликация:** Перед передачей в LLM chunks дедуплицируются по тексту `safe_norm`.

## 5. Группировка рисков

После анализа всего документа, сырой список рисков обрабатывается в `risk_grouping.py`:
- Риски со статусом `is_risky=False` игнорируются.
- Риски разбиваются по корзинам (buckets) в зависимости от их категории (`risk_category`).
- Внутри каждой категории ведется подсчет рисков уровня high, medium, low.
- Итоговые группы сортируются: в начале идут категории с наибольшим количеством критических (high) рисков, затем medium и т.д.
- Это позволяет фронтенду сразу отображать наиболее проблемные зоны контракта.

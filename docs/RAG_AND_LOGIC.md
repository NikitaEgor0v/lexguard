# RAG и Бизнес-логика

Модуль Legal Analyzer использует подход RAG (Retrieval-Augmented Generation) для предоставления LLM правового контекста перед принятием решения о наличии риска.

## 1. Векторизация и база данных (Qdrant)

За хранение и поиск эталонных правовых норм отвечает сервис `Qdrant`. 

- **Модель энкодера:** `intfloat/multilingual-e5-base`
- **Размерность вектора:** 768
- **Метрика дистанции:** Cosine Distance
- **Коллекция:** `legal_norms`

Все эталонные нормы (хранящиеся в `data/legal_norms.json`) преобразуются в векторы и помещаются в коллекцию Qdrant. Для каждой нормы сохраняются метаданные (payload): тип договора, категория риска, критичность, юридические паттерны и паттерны уловок.

## 2. Определение типа контракта

Перед началом покомпонентного RAG-анализа, система выполняет пред-анализ документа:
1. Берется превью договора: первый или два первых сегмента документа. Текст обрезается до 800 символов (`MAX_CLASSIFY_PREVIEW_CHARS`).
2. Превью отправляется в Ollama с промптом `CONTRACT_CLASSIFY_PROMPT`.
3. LLM определяет тип контракта (например, "аренда", "подряд", "нда").
4. Если LLM ошибается или не может определить, по умолчанию устанавливается тип `"иной"`.

## 3. RAG-поиск и фильтрация

Для каждого сегмента договора, который анализируется, происходит следующий алгоритм:
1. Сегмент переводится в вектор (`query: {текст}`).
2. Формируется объект фильтрации (`Filter` / `FieldCondition`), который требует совпадения поля `contract_type` с определенным типом контракта (с учетом алиасов) или универсальными типами (`все`, `all`).
3. Qdrant ищет ближайших соседей. Количество зависит от модели: `max_rag_norms` (2 для gemma2:2b, 4 для gemma3:12b+). По умолчанию `TOP_K = 2`.
4. Минимальный порог отсечения `SCORE_THRESHOLD = 0.75`. Все, что имеет сходство ниже — отбрасывается. **Примечание:** Порог повышен с 0.55 до 0.75 для снижения false positives от нерелевантных норм.
5. **Умная обрезка:** После сборки контекста происходит обрезка по `max_rag_chars` (500 для 2B, 2000 для 12B+), но всегда по границам норм (метод `_truncate_by_norm_boundaries`). Норма никогда не обрезается посередине — лишние нормы отбрасываются целиком.
6. Параллельно, если пользователь загрузил свои кастомные документы (`user_id` передан), система производит поиск по пользовательским эталонам.

## 4. LLM Анализ (Ollama)

Найденные эталонные нормы (стандартные и пользовательские) конкатенируются и вставляются в промпт для LLM вместе с самим сегментом.

- **Системный промпт:** Два варианта — компактный (`SYSTEM_PROMPT_COMPACT`, ~1300 символов) для малых моделей (gemma2:2b) и полный (`SYSTEM_PROMPT_FULL`, ~3200 символов) для больших моделей (gemma3:12b+). Выбор определяется полем `use_compact_prompt` в `ModelConfig`. Оба варианта содержат точные критерии для классификации `risk_level` (high, medium, low, none) и `risk_category`.
- **Анти-контаминация:** Промпты содержат явные блоки «АНТИ-КОНТАМИНАЦИЯ», запрещающие модели переносить риски из RAG-норм на сегмент. Ключевые правила:
  - `risk_description` ДОЛЖЕН описывать риск из текста сегмента, а не из RAG.
  - ЗАПРЕЩЕНО копировать `risk_description` из RAG-контекста, если риск не присутствует в тексте.
  - Если текст описывает нормальное условие (оплата за выполненное, возврат аванса) — `is_risky: false`.
- **Пост-обработка (`_validate_risk_relevance`):** После парсинга JSON, метод проверяет релевантность риска:
  - Если сегмент содержит **safe pattern** (напр. "оплачивает фактически выполненный", "после полной оплаты") — риск отклоняется.
  - Если сегмент не содержит **никаких ключевых слов риска** (штраф, неустойка, ответственность, права, суд) — риск отклоняется как false positive от RAG.
- **Безопасная формулировка (`safe_redaction`):** Для рисковых сегментов уровня `high` и `medium` LLM предлагает **ЗАМЕНУ** опасного текста. Промпт явно требует:
  - Вернуть ТОЛЬКО финальный безопасный текст.
  - НЕ начинать с опасной формулировки.
  - НЕ копировать оригинал в начало.
- **Пост-обработка (`_validate_safe_redaction`):** Проверяет, что safe_redaction:
  - Отличается от оригинала (отбрасывает дословные копии и тексты с >85% совпадением).
  - Не начинается с опасной фразы из оригинала (напр. "без оплаты", "неограниченную ответственность").
  - Для `low`/`none` рисков поле обнуляется.
- **Генерация:** Запрос отправляется в Ollama с параметрами конфигурации модели (задается через `get_model_config()`).
- **Фоллбек (Fallback):** Если Ollama недоступна, используется ручной метод на основе ключевых слов (словарный метод в `rag._fallback()`), который возвращает предупреждения по базовым категориям.

## 5. Группировка рисков

После анализа всего документа, сырой список рисков обрабатывается в `risk_grouping.py`:
- Риски со статусом `is_risky=False` игнорируются.
- Риски разбиваются по корзинам (buckets) в зависимости от их категории (`risk_category`).
- Внутри каждой категории ведется подсчет рисков уровня high, medium, low.
- Итоговые группы сортируются: в начале идут категории с наибольшим количеством критических (high) рисков, затем medium и т.д.
- Это позволяет фронтенду сразу отображать наиболее проблемные зоны контракта.

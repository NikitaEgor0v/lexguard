# RAG и Бизнес-логика

Модуль Legal Analyzer использует подход RAG (Retrieval-Augmented Generation) для предоставления LLM правового контекста перед принятием решения о наличии риска.

---

## 1. Векторизация и база данных (Qdrant)

| Параметр | Значение |
|----------|---------|
| Энкодер | `intfloat/multilingual-e5-base` |
| Размерность вектора | 768 |
| Метрика | Cosine Distance |
| Системная кол��екция | `legal_norms` |
| Пользовательская коллекция | `user_documents` |

Все эталонные нормы (`data/legal_norms.json`) преобразуются в векторы и помещаются в коллекцию `legal_norms`. Эмбеддинг строится по комбинации `safe_norm + risky_pattern` для более точного поиска.

Для каждой нормы сохраняются метаданные (payload): тип договора, категория риска, критичность, risky_pattern, legal_basis, topic.

---

## 2. Определение типа контракта

Перед началом анализа система выполняет пред-классификацию:

1. Берётся превью договора: `extract_smart_classification_preview()` анализирует начало и середину текста. Текст обрезается до `MAX_CLASSIFY_PREVIEW_CHARS = 1500` символов.
2. Дополнительно ищутся маркеры сторон (regex): арендодатель/арендатор, заказчик/исполнитель, поставщик/покупатель и т.д.
3. Превью отправляется в Ollama с промптом `CONTRACT_CLASSIFY_PROMPT`.
4. LLM определяет тип контракта одним словом: услуги, подряд, поставка, аренда, трудовой, лицензионный, нда, агентский, иной.
5. При ошибке LLM устанавливается тип `"иной"`.

## 3. RAG-поиск и фильтрация

Для каждого сегмента договора:

1. **Проверка нейтральности**: `is_neutral_segment()` проверяет regex-паттернами, является ли сегмент нейтральным (цена, реквизиты, подписи). Нейт��альные сегменты — сразу `is_risky: false` без RAG.

2. **Векторизация**: Сегмент переводится в вектор (`query: {текст}`).

3. **Фильтрация**: Формируется фильтр по `contract_type` с учётом алиасов (например, "услуги" ищет также "software_development", "outsourcing") и универсальных типов ("все", "all").

4. **Поиск**: Qdrant ищет ближайших соседей. `TOP_K = 6` (с последующей фильтрацией).

5. **Порог отсечения**: `MIN_RELEVANCE_SCORE` — конфигурируется через env (дефолт `0.50`), а в коде `MIN_RELEVANCE_SCORE_DEFAULT = 0.80`. Всё, что имеет сходство ниже — отбрасывается.

6. **Дедупликация**: Chunks с одинаковым `safe_norm` (SHA256 хеш первых 200 символов) не передаются дважды.

7. **Умная обрезка**: Контекст обрезается по `max_rag_chars`, но всегда по границам норм. Норма никогда не обрезается посередине.

### Пользовательские эталоны

Если пользователь загрузил свои документы (`user_id` передан), система производит объединённый поиск:

1. **Системные нормы** (коллекци�� `legal_norms`) — высший приоритет
2. **Пользовательские эта��оны** (коллекция `user_documents`) — персональный контекст

Пороги для пользовательских документов:
- `score < MIN_USER_DOC_SCORE (0.85)` → отбрасывается
- `0.85 ≤ score < CORPORATE_NORM_SCORE (0.90)` → помечается как `[ПОЛЬЗОВАТЕЛЬСКИЙ ЭТАЛОН]`
- `score ≥ 0.90` → помечается как `[КОРПОРАТИВНАЯ НОРМА]` (LLM обязан поставить `is_risky: false`)

Детерминированное слияние:
- Системные chunks идут первыми (юридический авторитет)
- Пользовательские chunks следуют (персональ��ый контекст)
- Общий лимит: `MAX_CHUNKS_PER_SEGMENT` (по умолчанию 3)
- Минимум 1 слот резервируется для пользовательского chunk при наличии документов

## 4. LLM Анализ (Ollama)

### Системный промпт

Единый промпт `SYSTEM_PROMPT` содержит:
- Формат JSON-ответа (is_risky, risk_level, risk_category, risk_description, recommendation, safe_redaction)
- Правило корпоративных норм (высший приоритет)
- Критическое правило сравнения с эталоном и риском
- Развёрнутые примеры правильной классификации
- Перечень нейтральных сегментов (11 категорий)
- Правила уровней риска

### Логика сравнения с эталоном

RAG-контекст структурирован для каждой нормы:
- **ЭТАЛОН (безопасная формулировка):** образец правильной формулировки
- **РИСК (опасная формулировка):** паттерн, который нужно выявлять
- **КАТЕГОРИЯ:** тип риска
- **ОСНОВАНИЕ:** ссылки на статьи ГК РФ

Алгоритм принят��я решения:
1. Если текст соответствует полю ЭТАЛОН → `is_risky: false, risk_level: none`
2. Если текст соответствует полю РИСК → `is_risky: true`, определяется risk_level
3. Само по себе наличие RAG-контекста **не означает** наличие риска

### Нейтральные сегменты (автоматически is_risky: false)

1. Сумма договора (только число и валюта)
2. Реквизиты сторон (ИНН, КПП, ОГРН, адреса)
3. Подписи и экземпляры
4. Дата вступления в силу
5. Форс-мажор с объективным критерием (ТПП, суд)
6. Симметричное расторжение (равное для обеих сторон)
7. Предмет договора с Техническим заданием
8. Допсоглашения обеими сторонами
9. Результат работ — перечень без ограничений
10. Ответственность стороны за свои материалы
11. Расторжение с оплатой фактически выполненного

### Правила классификации risk_level

| Уровень | Критерий |
|---------|---------|
| `high` | Штрафы без лимита, утрата прав без компенсации, неограниченная ответственность |
| `medium` | Размытые сроки, неопределённые обязательства, одностороннее изменение условий |
| `low` | Незначительные огрехи формулировки |
| `none` | Нейтральный, сбалансированный текст |

### Safe Redaction

Для рисков уровня `high` и `medium` модель генерирует `safe_redaction` — безопасную переформулировку:
- Содержит только новую безопасную формулировку
- Не содержит исходный опасный текст
- Валидируется через `SequenceMatcher` (overlap < 85%)
- Проверяется на `DANGEROUS_PHRASES` в начале строки

### Обработка

- **Последовательная**: Сегменты один за другим, GPU получает все ресурсы
- **Фоллбек**: Если Ollama недоступна — словарный метод (`_fallback()`)
- **Retries**: `MAX_LLM_RETRIES = 2` при ошибках
- **Таймаут**: `REQUEST_TIMEOUT_SEC` (по умолчанию 300 сек)

## 5. Группировка рисков

После анализа всего документа (модуль `risk_grouping.py`):
1. Риски со статусом `is_risky=False` игнорируются
2. Риски разбиваются по корзинам (buckets) по `risk_category`
3. Внутри категории подсчитываются high, medium, low
4. Итоговые группы сортируются: сначала категории с наибольшим количеством `high` рисков
5. Frontend отображает наиболее проблемные зоны первыми

## 6. AI-Чат по результатам

Модуль `ChatContextBuilder` собирает промпт для AI-ассистента:
- Фрагменты договора (до 1200 символов)
- Список рисков с нумерацией "Риск №1", "Риск №2" (до 2000 символов)
- История последних 6 сообщений (до 1000 сим��олов)
- Вопрос пользователя

Возможности ассистента:
- Объяснение рисков простым языком
- Генерация готовых формулировок (опирается на ГК РФ)
- Ответы про конкретные риски по номеру или пункты договора

Каждая чат-сессия привязана к конкретному `analysis_id` (паттерн Get-or-Create).

# API и Потоки Данных

Взаимодействие между Frontend и Backend построено на REST API. Из-за длительности анализа используется асинхронный паттерн с фоновыми задачами и polling.

---

## Основные эндпоинты

### `POST /api/v1/analyze`

**Назначение:** Загрузка документа (PDF/DOCX) и запуск анализа.

**Процесс:**
1. Проверка формата и размера файла (максимум 15 МБ)
2. Парсинг текста и разбиение на сегменты (`PreprocessorService`)
3. Валидация: документ не пустой, сегментов не более `MAX_SEGMENTS_PER_DOCUMENT` (500)
4. Генерация `analysis_id`, отправка задачи в Celery (`analyze_document_task.delay`)
5. Ответ: `202 Accepted` с `analysis_id` и статусом `processing`

Анализ идёт пакетно: сегменты обрабатываются последовательно, результаты сохраняются в БД каждые `ANALYSIS_BATCH_SIZE` (20) сегментов.

### `GET /api/v1/analyze/{analysis_id}`

**Назначение:** Получение статуса или результатов анализа.

**Процесс:**
1. Проверка существования анализа → 404 если не найден
2. Проверка владельца (IDOR Protection) → 403 если чужой
3. Если анализ завершён → полная структура `AnalysisResponse`
4. Если ещё идёт → прогресс из Redis (`progress:{analysis_id}`), отдаётся `progress_percent` и `progress_label`
5. Если Redis недоступен → дефолтное значение `0/1`
6. Если heartbeat устарел → анализ помечается как `failed`

### `GET /api/v1/analyze/{analysis_id}/grouped`

**Назначение:** Сгруппированные результаты для интерфейса.

**Процесс:**
1. Проверка owner-ship
2. Если `completed` → прогон через `group_analysis_risks`, возврат с `executive_summary`
3. Если `processing` → частичные результаты (только сохранённые пакеты)
4. `executive_summary = null` до полного завершения

### `GET /api/v1/analyses`

**Назначение:** История анализов пользователя (с пагинацией).

### `GET /api/v1/status`

**Назначение:** Статус системы (Ollama, модель, RAG, конфигурация).

### `GET /health`

**Назначение:** Health-check бэкенда.
Ответ: `{"status": "healthy"}`

## Аутентификация

### `POST /api/v1/auth/register`
Регистрация нового пользователя. Пароль хешируется bcrypt.

### `POST /api/v1/auth/login`
Вход. Возвращает JWT-токен.

Все защищённые эндпоинты требуют заголовок `Authorization: Bearer <token>`.

---

## Пользовательские эталоны (Documents API)

### `POST /api/v1/documents/upload`
Загрузка эталонного документа (PDF/DOCX/текст). Текст разбивается на chunks и индексируется в Qdrant (коллекция `user_documents`).

### `GET /api/v1/documents`
Список загруженных эталонов пользователя.

### `DELETE /api/v1/documents/{id}`
Удаление эталона (из PostgreSQL и Qdrant).

### `POST /api/v1/documents/upload/text`
Создание эталона из текста (используется кнопкой «Принять как норму компании» в UI).

---

## Chat API

### `POST /api/v1/chat/session`
Создание или получение чат-сессии для анализа (Get-or-Create по `analysis_id`).

### `POST /api/v1/chat/session/{session_id}/message`
Отправка сообщения в чат. Ответ AI генерируется синхронно.

### `GET /api/v1/chat/session/{session_id}`
Получение чат-сессии с историей сообщений.

### `GET /api/v1/chat/sessions`
Список всех чат-сессий пользователя.

## Frontend Data Flow

Фронтенд (`frontend/js/`) построен на модульной архитектуре:

| Файл | Назначение |
|------|-----------|
| `api.js` | Центральный `apiFetch()` — заголовки, обработка 401, JSON-ошибки |
| `upload.js` | Загрузка файла, запуск анализа |
| `analysis.js` | Polling прогресса, рендер карточек рисков, кнопка "Принять как норму" |
| `chat.js` | AI-чат, pendingSessions, typing indicator |
| `documents.js` | Управление эталонами |
| `history.js` | История анализов |
| `auth.js` | Авторизация/регистрация |
| `app.js` | Инициализация, роутинг |
| `theme.js` | Переключение темы |

### Polling-механизм (analysis.js)

1. После запуска анализа клиент каждые 3 секунды опрашивает `/api/v1/analyze/{id}`
2. Параллельно запрашивает `/analyze/{id}/grouped` для получения частичных результатов
3. Новые риск-карточки рисуются инкрементально (бесконечная лента)
4. При `status: completed` — финальный вызов `/analyze/{id}/grouped` для полной отрисовки с Executive Summary

### Чат (chat.js)

- `pendingSessions` — объект для хранения состояния ожидания каждой сессии
- Page Visibility API для перезапуска анимации при возврате на вкладку
- При переключении между чатами состояние ожидания сохраняется
- Typing indicator: анимация точек + текст "Ассистент думает..."

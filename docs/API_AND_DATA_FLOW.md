# API и Потоки Данных

Взаимодействие между Frontend-клиентом и Backend-сервером построено на REST API. В связи с длительным процессом анализа, используется асинхронный паттерн с фоновыми задачами и поллингом (polling).

## Основные эндпоинты

### `POST /api/v1/analyze`
**Назначение:** Загрузка документа (PDF/DOCX) и запуск анализа.
**Процесс:**
1. Проверка формата и размера файла (максимум 15 МБ).
2. Запуск препроцессора (`PreprocessorService`), который парсит текст и разбивает его на сегменты.
3. Валидация: Документ не должен быть пустым. Максимальное число сегментов настраивается через `MAX_SEGMENTS_PER_DOCUMENT` (по умолчанию 500, 0 = без ограничения).
4. Генерация `analysis_id` и отправка задачи в очередь Celery (`analyze_document_task.delay`). Анализ идет пакетно: сегменты разбиваются на пачки по `ANALYSIS_BATCH_SIZE` (по умолчанию 20), каждая пачка сохраняется в БД сразу после обработки.
5. **Ответ:** `202 Accepted` с `analysis_id` и статусом `processing`.

### `GET /api/v1/analyze/{analysis_id}`
**Назначение:** Получение статуса или результатов анализа.
**Процесс:**
1. Бэкенд проверяет наличие результата в PostgreSQL. Если анализ завершен, возвращается полная структура `AnalysisResponse`.
2. Если анализ еще идет, бэкенд обращается в Redis за ключом `progress:{analysis_id}`.
3. Формируется прогресс (например `45/80`) и отдается на фронтенд в виде `progress_percent` и текстового `progress_label`.
4. Если Redis недоступен, бэкенд не падает, а отдает дефолтное значение прогресса `0/1`.

### `GET /api/v1/analyze/{analysis_id}/grouped`
**Назначение:** Получение сгруппированных результатов для отображения в интерфейсе.
**Процесс:**
1. Загрузка данных анализа из БД.
2. Если анализ завершен (`completed`), прогон данных через функцию `group_analysis_risks` и возврат полной структуры с `executive_summary`.
3. Если анализ ещё в процессе (`processing`), возвращаются **частичные результаты** — только те пакеты, которые уже сохранены в БД. Ответ содержит дополнительные поля: `status`, `total_segments`, `analyzed_segments`.
4. `executive_summary` равно `null` до полного завершения анализа (нельзя сгенерировать сводку, не имея всех данных).

### `GET /api/v1/analyses`
**Назначение:** Получение истории анализов пользователя (с пагинацией).

## Frontend Data Flow

Во фронтенде (`frontend/js`) работа с API обернута в центральный механизм в `api.js`.
- Функция `apiFetch` автоматически подставляет заголовки, обрабатывает 401 ошибки (Unauthorized) и вытягивает сообщения об ошибках из JSON.
- В файле `analysis.js` реализован поллинг: клиент делает запросы к `/api/v1/analyze/{id}` каждые 3 секунды, обновляя UI прогресс-бара.
- Параллельно с поллингом статуса клиент запрашивает `/analyze/{id}/grouped` для получения частичных результатов и отрисовывает новые риск-карточки инкрементально (бесконечная лента).
- Как только сервер возвращает `status: completed`, клиент выполняет финальный вызов `/analyze/{id}/grouped` для полной отрисовки с Executive Summary.

## [2026-05-09] Fix: safe_redaction and RAG-contamination

### Проблема
1. `safe_redaction` всегда был `null` (отбрасывались правильные редакции).
2. RAG притягивал нерелевантные фрагменты для нейтральных сегментов (контаминация нейтральных пунктов).

### Решение
1. **safe_redaction**:
   - Заменена агрессивная логика проверки пересечения слов (на базе множеств) на `SequenceMatcher` с порогом 0.85.
   - Проверка начала строки по первым символам оригинала заменена на статический список `DANGEROUS_PHRASES`.
   - Разрешено возвращать `safe_redaction` не только для `HIGH`, но и для `MEDIUM` рисков.
2. **RAG-контаминация**:
   - Порог `MIN_RELEVANCE_SCORE_DEFAULT` повышен с 0.50 до 0.72.
   - Эмбеддинг при индексации теперь строится по комбинации `safe_norm` + `risky_pattern`, что позволяет искать ближе к реальному риску.
   - Исправлена регулярка для цены в `is_neutral_segment` и подключён список `NEUTRAL_SEGMENT_PATTERNS`.
   - В `_classify_contract_type` увеличено превью до 1500 символов, добавлено чтение середины длинных документов.

### Изменённые файлы
- `backend/services/analyzer.py`
- `backend/services/rag.py`
- `backend/config/model_registry.py`

## [2026-05-09] Chat: Расширены возможности AI-ассистента

### Проблема
AI-ассистент в чате отвечал слишком ограниченно из-за строгого системного промпта. При запросе "сгенерируй правильный пункт договора" модель вместо генерации текста давала общие рекомендации о том, что нужно сделать.

### Причина
Инструкция "Используй **только** контекст договора и результатов анализа" интерпретировалась моделью буквально, что блокировало генерацию нового контента.

### Решение
Переработан системный промпт в `ChatContextBuilder`:
- Явно перечислены возможности ассистента: генерация текста, предложение альтернатив, объяснение рисков
- Добавлена инструкция "Если просят сгенерировать текст — генерируй готовый к использованию текст"
- Сохранены ограничения на выдумывание несуществующих рисков
- Модель теперь может опираться на нормы ГК РФ при генерации формулировок

### Дополнительное исправление: нумерация рисков
**Проблема:** Пользователь спрашивал про "6-й риск", а модель генерировала "пункт 6 договора". Риски нумеровались по внутреннему segment_id, а не по порядку отображения.

**Решение:**
- `_build_risks_text()` теперь нумерует риски как "Риск №1", "Риск №2" — по порядку
- Добавлен preview текста риска для лучшего контекста
- В промпт добавлена инструкция о интерпретации номеров рисков

### Изменённые файлы

## [2026-05-08] Fix Risk Classification Logic — Etalon vs Risk Comparison

### Проблема
Модель классифицировала безопасные формулировки как рискованные. Precision на сбалансированном контракте = 19% (13 false positives из 16).

Примеры ошибок:
- "Права переходят после полной оплаты" → помечалось как риск (хотя это эталонная формулировка)
- "Оплата в два этапа: 50% аванс, 50% после акта" → помечалось как риск (хотя есть аванс)
- "Изменения через допсоглашения" → помечалось как риск (хотя это защита)
- "Стоимость 180 000 рублей" → помечалось как риск (просто сумма)

### Причина
Модель реагировала на ТЕМУ сегмента (права, оплата, расторжение), а не на СМЫСЛ. Если RAG находил релевантный chunk, модель почти всегда ставила is_risky: true.

### Изменения

#### Промпт (analyzer.py)
- **Добавлено КРИТИЧЕСКОЕ ПРАВИЛО СРАВНЕНИЯ**: Если текст соответствует полю "Эталон" из RAG → is_risky: false. Риск фиксируется ТОЛЬКО если текст соответствует полю "Риск".
- **Добавлены примеры применения правила** прямо в промпт для clarity
- **Добавлен раздел НЕЙТРАЛЬНЫЕ СЕГМЕНТЫ**: суммы, реквизиты, подписи, допсоглашения → всегда is_risky: false
- **Восстановлена генерация safe_redaction** для рисков уровня high

#### Парсинг (analyzer.py)
- **Добавлен парсинг safe_redaction** из ответа LLM
- **Добавлена валидация safe_redaction**: не должна содержать исходный опасный текст, не должна начинаться с опасных фраз, overlap <60%

#### RAG (rag.py)
- **Добавлена дедупликация chunks**: одинаковые нормы (по safe_norm) не передаются дважды

### Ожидаемый результат

Контракт 47 (сбалансированный):
- risky_segments = 3 (п. 2.3, п. 4.1, п. 6.2)
- п. 1.3 (права после оплаты) → is_risky: false
- п. 2.1 (сумма 180 000) → is_risky: false
- п. 2.2 (аванс + окончательный) → is_risky: false
- п. 5.3 (возврат аванса) → is_risky: false
- п. 6.3 (допсоглашения) → is_risky: false

Контракт 12 (токсичный):
- risky_segments = 9 (все реальные риски найдены)
- п. 2.1 (сумма 100 000) → is_risky: false
- Для high-рисков: safe_redaction заполнена

## [2026-05-08] Stabilized Frontend API Proxy on Docker Restarts

### Проблема
После перезапуска backend фронтенд снова периодически показывал `сервер недоступен`, а авторизация/профиль отдавали `502`.

### Причина
Nginx во frontend продолжал использовать старый внутренний IP backend-контейнера после рестарта (`connect() failed ... upstream ... connection refused`).

### Изменения
- В `nginx/default.conf` проксирование API переведено на стабильный endpoint:
  - `proxy_pass http://host.docker.internal:8000;`
- Для health-check пути также обновлен upstream:
  - `proxy_pass http://host.docker.internal:8000/health;`
- Перезапущен `frontend` контейнер для применения нового конфига.

### Проверка
- `GET /api/v1/status` через `localhost:3000` возвращает `200 OK`.
- `POST /api/v1/auth/login` через `localhost:3000` возвращает `200 OK`.
- Ошибки `502 Bad Gateway` на API больше не воспроизводятся после перезапуска.

## [2026-05-08] Fix False "Analysis Interrupted" During Long Runs

### Проблема
Во время долгого анализа UI показывал ошибку: «Процесс анализа неожиданно прерван», хотя Celery-задача фактически продолжала выполняться и позже сохраняла результат в историю.

### Причина
После упрощения `analyzer.py` heartbeat-ключ в Redis перестал регулярно обновляться.
Маршрут `/analyze/{id}` считал heartbeat устаревшим и помечал анализ как `failed` по таймауту.

### Изменения
- В `services/analyzer.py` возвращено регулярное обновление heartbeat:
  - при старте анализа;
  - перед/после обработки каждого сегмента;
  - внутри `_call_llm()` перед запросом, после ответа и в `finally` каждой попытки.
- Добавлен helper `AnalyzerService._update_heartbeat(...)` для единообразного безопасного обновления Redis-ключа.

### Результат
- Долгие анализы больше не получают ложный статус `failed` при активной обработке.
- Сообщение о «неожиданном прерывании» показывается только при реальном зависании/падении воркера.

#### Веса рисков (analyzer.py `_summary`)

## [2026-05-07] Anti-contamination & RAG Relevance Improvements

### Проблема
При анализе контрактов система демонстрировала следующие баги:
1. **RAG-контаминация**: `risk_description` копировался из RAG-контекста, а не из текста сегмента
2. **False positives**: Безопасные пункты (напр. "оплата за выполненную работу") помечались как рискованные
3. **safe_redaction**: Иногда начинался с опасной формулировки
4. **Пропуск рисков**: Сегменты о подсудности не обнаруживались

### Изменения

#### RAG (rag.py)
- **SCORE_THRESHOLD**: повышен с `0.55` до `0.75` для снижения false positives от нерелевантных норм

#### Промпты (analyzer.py)
- Добавлено явное правило **АНТИ-КОНТАМИНАЦИЯ** в SYSTEM_PROMPT_COMPACT и SYSTEM_PROMPT_FULL
- Запрещено копировать `risk_description` из RAG, если риск не присутствует в тексте сегмента
- Добавлены примеры ошибок в промпт для clarity
- Расширен список рисков: добавлены "подсудность", "претензионный порядок"

#### Классификатор (analyzer.py `_classify_risk`)
- Расширен список признаков риска: добавлены подсудность, юрисдикция, претензионный порядок

#### Пост-обработка (analyzer.py)
- **Новый метод `_validate_risk_relevance`**: проверяет релевантность риска тексту сегмента
  - Отклоняет риски для сегментов с safe patterns
  - Отклоняет риски если сегмент не содержит ключевых слов риска
- **Улучшен `_validate_safe_redaction`**: проверяет что safe_redaction не начинается с опасной фразы
- **SAFE_PATTERNS**: список безопасных формулировок которые не должны помечаться как рискованные
- **DANGEROUS_PHRASES**: список опасных фраз которые не должны появляться в начале safe_redaction
